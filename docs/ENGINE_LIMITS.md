# Расширяемость таблиц: что показал разбор кода

Ранее в [CONTENT_BUDGET.md](CONTENT_BUDGET.md) вопрос «можно ли добавлять записи
в таблицы» был помечен как требующий запуска игры. Это оказалось не нужно:
ответ читается прямо из `dlords.exe`.

Метод: разбор PE-образа, поиск строк с именами файлов, дизассемблирование
загрузчиков (`dl_toolkit.pe`, `dl_toolkit.itemtab`, capstone x86-32).

---

## 1. Итог

| Таблица | Как движок её грузит | Расширяема? | Потолок |
|---|---|---|---|
| `D6TRLIST.DAT` | читает счётчик из записи 0, `malloc((count+1)*60)`, цикл чтения по 60 Б | **да** | **255** (сейчас 222) |
| `D6PROP.DAT` | явная проверка `cmp id, 0x280`, статический кэш указателей | **да** | **640** (сейчас 560) |
| `D6MONS.DAT` | `lseek(index*340)` + `read(340)` на каждую запись | **да** | не найден |
| `D6NPC.DAT` | `lseek(index*36)` + `read(36)` на каждую запись | **да** | не найден |
| `D6MONSND.DAT`, `D6TREAS.DAT` | открываются по имени в рантайме | вероятно да | не проверялся |
| `iname.dat` | грузится целиком | да, но см. §4 | — |
| `mname.dat` | грузится целиком, доступ через жёсткие границы | **нет** | 435 записей, id 385–819 |
| **`D6ITEM.DAT`** | **не открывается вообще** | **файл мёртв** | см. §3 |

Вывод: **три таблицы расширяемы уже сейчас**, ещё две — почти наверняка.
Прежняя оценка «всё заблокировано» была слишком осторожной.

## 2. Доказательства

### 2.1. `D6TRLIST.DAT` — динамическое выделение

`LoadTLISTS` (VA `0x0053C870`):

```asm
call  fopen                      ; "D6TRLIST.DAT"
push  0 / push 0 / push ebx
call  fseek                      ; в начало
push  ebx / push 1 / push 4 / push 0x7db8cc
call  fread                      ; читаем uint32 count из записи 0
mov   eax, [0x7db8cc]
cmp   eax, 0x100                 ; 256
jl    ok
      ...сообщение...            ; предупреждение, не выход
ok:
lea   eax, [eax + eax*2 + 3]     ; 3*count + 3
lea   ecx, [eax + eax*4]         ; 15*count + 15
shl   ecx, 2                     ; (count + 1) * 60
call  malloc                     ; ← размер вычисляется из файла
...
loop:
  fseek(f, i*60, SEEK_SET)
  fread(ptr, 1, 0x3c, f)         ; 60 байт на запись
  add   edi, 0x3c
  add   esi, 4                   ; таблица указателей 0x806C20
  cmp   ebp, count
  jle   loop
```

Память выделяется **по счётчику из файла**. Ограничение — статический массив
указателей по адресу `0x806C20`; порог `0x100` в коде указывает на его размер.
Отсюда безопасный потолок **255 записей**: сейчас 222, то есть **+33 списка**.

### 2.2. `D6PROP.DAT` — явный предел 640

Загрузчик (VA `0x0050DCE0`) начинается с проверки:

```asm
cmp   edi, 0x280        ; 640
jl    ok
      push edi          ; иначе — сообщение об ошибке с номером props
      jmp  error
ok:
mov   eax, [edi*4 + 0x9de5c0]   ; кэш указателей на 640 элементов
```

Сейчас занято 560 → **+80 записей** доступно.

### 2.3. `D6MONS.DAT` и `D6NPC.DAT` — чтение по индексу

Чтение записи монстра (VA `0x0049B980`):

```asm
mov   edx, 0x154                 ; 340 — размер записи
mov   ecx, 1
call  calloc                     ; буфер ровно на ОДНУ запись
push  0x8000 / push "D6MONS.DAT"
call  open
mov   eax, ebx                   ; ebx = индекс монстра
shl   eax, 4                     ; *16
add   eax, ebx                   ; *17
lea   eax, [eax + eax*4]         ; *85
shl   eax, 2                     ; *340
push  eax
call  lseek                      ; lseek(fd, index*340, SEEK_SET)
push  0x154 / push ebp / push esi
call  read                       ; read(fd, buf, 340)
call  close
```

Таблица целиком в память не загружается, статического массива на 819 записей
нет, счётчик из записи 0 в этом пути вообще не читается. Файл можно дописывать:
`lseek` дойдёт до нового смещения.

`D6NPC.DAT` устроен так же, шаг 36 байт (`lea eax,[ebp+ebp*8]; shl eax,2`).

## 3. Главное открытие: `D6ITEM.DAT` движком не читается

В `dlords.exe` **нет ни одной строки**, содержащей `D6ITEM` или `ITEM.DAT`
(проверено регистронезависимо; для контроля `D6MONS.DAT`, `D6TRLIST.DAT`,
`D6PROP.DAT` и остальные в образе присутствуют).

Настоящая таблица предметов строится функцией `MakeITEMS()` (VA `0x004ED670`) —
это **116 609 байт кода, около 20 000 инструкций**, которые заполняют
статический массив непосредственными записями:

```asm
mov   ecx, dword ptr [0x0065BA6C]   ; "CHAIN MITTENS" из .rdata
mov   dword ptr [0x030DF5A4], ecx   ; имя записи 2
mov   word  ptr [0x030DF5CC], 0x68  ; поле +0x28 записи 3
mov   dword ptr [0x030DF5E0], 0x2EE
```

Разбор функции даёт параметры массива:

| Параметр | Значение |
|---|---|
| База | `0x030DF40C` |
| Шаг записи | **204** байта |
| Записей | **948** (индексы 0…947) |
| Размер | 193 392 байта |
| Различных смещений полей | 70 |
| Присваиваний в разборе | 10 458 |

### Это закрывает старую загадку

Все предыдущие отчёты фиксировали противоречие: `iname.dat` id 4 = `CHAIN BOOTS`,
а `D6ITEM.DAT` запись 4 = `Vampire's Bite`, и делали вывод «разные пространства
id, мост не найден».

Моста нет, потому что **`D6ITEM.DAT` — не таблица предметов.** Соответствие
такое:

| `iname.dat` id | индекс в exe | имя |
|---:|---:|---|
| 1 | 0 | PUNCH |
| 2 | 1 | BAT BITE |
| 3 | 2 | CHAIN MITTENS |
| 4 | 3 | CHAIN BOOTS |

То есть `iname_id = index + 1`, ровно 948 записей с обеих сторон. Соответствие
однозначное.

`D6ITEM.DAT` содержит совершенно другой набор (`swings at $`, `Willow Arrow`,
`Heal Potion`) — вероятно, данные более ранней версии движка, оставшиеся в
поставке. Редактирование этого файла ни на что не влияет.

### Что из этого следует

| | |
|---|---|
| Переименование предметов | работает через `iname.dat`, **без патча exe** |
| Изменение характеристик | требует правки непосредственных операндов в `MakeITEMS` |
| Добавление предметов | требует расширения массива и вставки кода — тяжело |
| Правка `D6ITEM.DAT` | бессмысленна |

Патч характеристик механически прост: значения записаны как `mov [абс.адрес], imm`,
длина инструкции при правке операнда не меняется, перемещений и релокаций нет.
Модуль `dl_toolkit.itemtab` уже извлекает все 10 458 присваиваний с адресами
инструкций — этого достаточно, чтобы собрать патчер.

## 4. Жёсткие границы имён монстров

В том же обработчике `D6MONS` после чтения записи:

```asm
cmp   ebx, 0x181         ; 385
jl    skip
cmp   ebx, 0x334         ; 820
jge   skip
lea   eax, [ebx - 0x181] ; index - 385
cmp   eax, 0x1B3         ; 435
jge   skip
mov   edi, [eax*4 + 0x3117040]   ; таблица имён из mname.dat
```

Отображаемое имя берётся из `mname.dat` **только для id 385…819**. Это объясняет,
почему в `mname.dat` ровно 435 записей с id 385–819, и означает:

* записи `D6MONS` 1…384 отображаемого имени из `mname.dat` не получат;
* расширение `mname.dat` сверх 435 записей ничего не даст — граница в коде.

Это **корректирует план по монстрам**: 384 безымянные записи переиспользовать
можно, но имена им придётся давать иначе (внутреннее имя записи) либо патчить
границы в exe — три константы, `0x181`, `0x334`, `0x1B3`.

## 6. Что осталось проверить

| № | Вопрос | Как |
|---|---|---|
| 1 | Есть ли верхняя граница у индекса монстра со стороны вызывающих | найти всех, кто передаёт индекс в загрузчик |
| 2 | То же для NPC | аналогично |
| 3 | Загрузчики `D6TREAS.DAT` и `D6MONSND.DAT` | дизассемблировать по ссылкам на строки |
| 4 | Где хранятся стартовые характеристики рас | искать таблицу рядом с обработчиком создания персонажа |
| 5 | Кривая опыта | искать таблицу уровней |
| 6 | Семантика 70 полей записи предмета | сопоставить значения с известными предметами из `iname.dat` |

Пункт 6 стал реалистичным: у нас есть 948 записей с известными именами и 10 458
присваиваний с точными смещениями. Сопоставление «поле → смысл» теперь задача
статистики, а не догадок.
