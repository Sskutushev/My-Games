# Современный стек и слоёные БД: что здесь работает, а что нет

Документ отвечает на вопрос: переписать ли всё на TypeScript/Node/Go/Python с
ClickHouse, Postgres, CockroachDB и Redis под кэш.

Короткий ответ: **для рантайма — нет, это не тот класс задач. Для пайплайна
разработки и телеметрии — да, и это стоит сделать.**

---

## 1. Числа, из которых всё следует

| Что | Объём |
|---|---:|
| Таблицы `.DAT` | 710 720 Б |
| Скрипты NPC (`npccode`) | 1 495 674 Б |
| Региональные данные | 538 143 Б |
| Таблица предметов внутри `dlords.exe` | 193 392 Б |
| **Все игровые данные** | **2 937 929 Б = 2.80 МБ** |
| Вся установка | 3 095 098 565 Б = 2.88 ГБ |
| **Доля данных от установки** | **0.095 %** |

Все игровые данные — **2.8 МБ**. Это меньше, чем одна текстура ландшафта.
Остальные 99.9 % — модели, текстуры, звук, видео, ландшафт.

Для 2.8 МБ распределённая СУБД не нужна. Эти данные помещаются в кэш процессора
целиком и читаются индексацией массива.

## 2. Почему БД в рантайме — категориальная ошибка

Движок обращается к таблицам внутри игрового цикла:

* попадание по цели → характеристики оружия;
* кадр отрисовки → модель и текстура предмета в руках;
* тик боя → сопротивления монстра;
* выпадение добычи → лут-лист.

Это 60 раз в секунду, десятки-сотни обращений за кадр. Бюджет кадра при 60 fps —
16.7 мс на всё: физику, ИИ, отрисовку.

| Способ доступа | Задержка | Во сколько раз медленнее массива |
|---|---:|---:|
| Индексация массива в памяти | ~1 нс | 1× |
| Redis, локальный сокет | ~100 000 нс | ~100 000× |
| Postgres, локально | ~200 000 нс | ~200 000× |
| ClickHouse, точечный запрос | ~1 000 000 нс | ~1 000 000× |

Одно обращение к Redis съедает 0.6 % бюджета кадра. Сто обращений — 60 %.
Игра станет неиграбельной ради данных, которые и так лежат в памяти.

Дело не в том, что эти базы плохие. Они решают задачи, которых у однопользовательской
action-RPG нет:

| Инструмент | Для чего создан | Есть ли эта задача здесь |
|---|---|---|
| PostgreSQL | ACID, конкурентные писатели, целостность | Писатель один — игрок. Нет |
| CockroachDB | Распределённый консенсус, мультирегион | Распределять нечего. Нет |
| ClickHouse | Аналитические сканы по миллиардам строк | 948 предметов. Нет |
| Redis | Разделяемое состояние между процессами | Процесс один. Нет |

Так не делает ни один движок: в Unity данные проектируются как `ScriptableObject`
и **компилируются** в сериализованные бандлы; в Unreal `DataTable` **кукается** в
плоские ассеты. База — на этапе авторинга, в сборке её уже нет.

## 3. Где эти инструменты действительно нужны

Правильная схема разносит авторинг, рантайм и аналитику:

```
  АВТОРИНГ                СБОРКА                РАНТАЙМ
  ┌──────────────┐      ┌──────────┐      ┌──────────────┐
  │  PostgreSQL  │─────▶│ компилятор│─────▶│ плоские      │
  │  источник    │      │ данных    │      │ бинарные     │
  │  истины      │      │ + валидация│     │ таблицы      │
  └──────────────┘      └──────────┘      └──────┬───────┘
        ▲                                        │
        │ редактор                               │ события
  ┌─────┴────────┐                        ┌──────▼───────┐
  │ TypeScript / │                        │  ClickHouse  │
  │ веб-интерфейс│◀───────────────────────│  телеметрия  │
  └──────────────┘        отчёты          └──────────────┘
```

### PostgreSQL — источник истины дизайна

Сейчас данные лежат в YAML (`data/obsidian_gate/ruleset.yaml`). Для одного
человека этого хватает. Postgres становится оправдан, когда появляются:

* несколько редакторов одновременно;
* ссылочная целостность на уровне БД (класс → навык, лут-лист → предмет);
* история изменений с авторством по каждому полю;
* запросы вида «все предметы, доступные Латнику до 10 уровня».

Схема ложится естественно: `items`, `monsters`, `loot_lists`, `loot_entries`,
`classes`, `skills`, `class_skill_caps`, `quests`, `dialogue_topics`.
Ограничения БД заменяют половину ручной валидации.

Миграции — те же, что уже есть в проекте, только на `alembic` вместо
самописного раннера.

### TypeScript / Node — редактор

Веб-интерфейс поверх Postgres: таблицы предметов, дерево классов, граф квестов,
предпросмотр лут-листов. Здесь TS уместен полностью — это обычное CRUD-приложение
с нетривиальным UI. Node для API, React/Svelte для интерфейса.

Именно так устроены внутренние редакторы в студиях: движок на C++, редактор
контента — веб-приложение.

### ClickHouse — телеметрия

Появляется смысл, когда есть играющая сборка, отправляющая события:
смерти по регионам, фактические частоты выпадения, время прохождения квестов,
на каком уровне игроки бросают игру.

Это как раз колоночные сканы по миллионам строк — родная задача ClickHouse.
Балансировать вслепую хуже, чем по данным.

### Redis — только для сетевой игры

Dungeon Lords поддерживает 2–8 игроков по UDP 2606. Если делать свой мастер-сервер:
сессии, матчмейкинг, состояние лобби. Для характеристик предметов — нет.

### CockroachDB — не нужен

Распределённый SQL решает мультирегиональную доступность на запись. У проекта
нет ни регионов, ни распределённой записи. Добавит операционную сложность без
единой решённой задачи.

## 4. Языки: где какой уместен

| Язык | Инструменты | Пайплайн сборки | Сервер | Рантайм игры |
|---|:--:|:--:|:--:|:--:|
| Python | **да** (сейчас) | да | нет | нет |
| TypeScript / Node | да (редактор) | да | да | только для браузерной игры |
| Go | да | **да** | **да** | нет (GC в мягком реалтайме) |
| Rust | да | да | да | **да** |
| C# | да | да | да | **да** (Godot, Unity) |
| C++ | — | — | да | **да** |

Python выбран для тулкита правильно: реверс-инжиниринг, разбор бинарных форматов,
дизассемблирование, генерация данных. Для рантайма он не годится, но рантайм мы и
не пишем.

## 5. Переписать движок: чего это стоит на самом деле

Вопрос «переписать на современном решении» на практике означает написать заново:

| Подсистема | Что придётся сделать |
|---|---|
| Рендер | BSP + ландшафт + освещение + вода, замена Shader Model 2.0 |
| Анимация | Скелетная система вместо Granny runtime |
| Физика и коллизии | С нуля |
| Навигация | Pathfinding по данным `.nvs`/`.PTH` |
| Бой и RPG-логика | 6 атрибутов, 45 навыков, 35 классов, статусы, сопротивления |
| ИИ | Поведение монстров и NPC |
| Событийная VM | 182 примитива из `EVENTS.DCL` |
| Интерпретатор скриптов NPC | 90 операторов |
| UI | Инвентарь, персонаж, журнал, торговля |
| Сохранения | Формат сегментов `D6SEGnn.GAM` |
| Сеть | 2–8 игроков |

Это работа масштаба «сделать игру», а не «поменять хранилище».

### Настоящий блокер — не движок, а ассеты

Даже написав идеальный рантайм, рисовать будет нечего:

| Ассет | Объём | Состояние |
|---|---:|---|
| Модели и анимации `.GR2` | 4964 файла, 538 МБ | Нужен коммерческий Granny SDK от RAD |
| Геометрия уровней `.bsp`/`.twd` | 40 наборов, 420 МБ | Формат не разобран |
| Ландшафт `TERRDATA.*` | 215 МБ | Формат не разобран |
| Озвучка `speech.dat` | 1.01 ГБ | Контейнер `SFFS` не разобран |

Порядок работ при таком переписывании обратный интуитивному: сначала декодеры
ассетов, и только потом выбор языка и движка. Выбор БД — вообще последний вопрос.

Плюс юридическое: конвертировать ассеты для себя можно, распространять — нет.
Публичный проект на этих ассетах жить не сможет.

## 6. Рекомендация

Две дорожки, независимые друг от друга.

### Дорожка A — работает сегодня

DEEP6 остаётся рантаймом, современным делаем **пайплайн**:

| Шаг | Состояние |
|---|---|
| Кодеки с доказанным round-trip | **готово**, 169/169 |
| Безопасная запись с откатом | **готово** |
| Валидация дизайна | **готово** |
| CI: линт, типы, тесты, миграции, сборка | **готово** |
| Патчер характеристик предметов в exe | следующий шаг, данные уже извлечены |
| Postgres как источник истины вместо YAML | когда редакторов станет больше одного |
| Веб-редактор на TS | после Postgres |
| ClickHouse для телеметрии | когда появится играющая сборка |

Здесь Postgres, TypeScript и ClickHouse уместны — но как **инструменты
разработки**, а не как рантайм.

### Дорожка B — новая игра, если хочется свой движок

Тогда честнее не переписывать Dungeon Lords, а сделать игру по мотивам на
готовом движке:

* **Godot 4** — открытый, C#/GDScript, 3D достаточно для такой игры;
* **Bevy (Rust)** — если нужен полный контроль;
* собственные ассеты, никаких юридических вопросов;
* дизайн из [OBSIDIAN_GATE_GDD.md](OBSIDIAN_GATE_GDD.md) переносится целиком —
  он не завязан на движок, кроме числа слотов;
* данные — Postgres на авторинге, компиляция в плоские ресурсы, ClickHouse на
  телеметрию. Ровно схема из §3.

Дорожка B не требует ни одного декодера закрытых форматов. Она дороже по
разработке, но не имеет блокеров.

## 7. Итог

| Идея | Вердикт |
|---|---|
| Redis/Postgres/ClickHouse как рантайм-хранилище игры | **Нет.** 2.8 МБ данных, доступ 60 раз в секунду, БД медленнее массива в 10⁵ раз |
| CockroachDB | **Нет.** Нечего распределять |
| Postgres как источник истины дизайна | **Да**, когда редакторов больше одного |
| TypeScript/Node для редактора контента | **Да** |
| ClickHouse для телеметрии баланса | **Да**, когда появится играющая сборка |
| Redis для сетевых сессий | **Да**, если делать мастер-сервер |
| Go для пайплайна и сервисов | **Да**, разумная альтернатива Python |
| Переписать DEEP6 на современном движке | **Технически возможно, но блокер — ассеты, а не движок.** Сначала декодеры |
| Сделать новую игру на Godot/Bevy по этому дизайну | **Да**, единственный путь без блокеров |
